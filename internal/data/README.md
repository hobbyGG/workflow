# Data

The data layer implements the repository interfaces defined by `biz`. It is a
business-aware adapter for external data sources, not a traditional DAO layer.
Database, cache, remote service, and Temporal details remain internal to this
package.

## Responsibilities

The data layer may:

- orchestrate one or more sqlc queries to satisfy a repository operation;
- call remote services required to satisfy a repository operation;
- assemble data from multiple tables into the shape required by `biz`;
- convert persistence models into biz entities;
- map database, driver, and remote-service errors to biz errors;
- report missing related data as an internal consistency error instead of
  silently returning incomplete data.

Core business decisions and invariants belong in `biz`, not in data.

## Dependency Boundaries

- Repository implementations must not depend on or call one another. For
  example, `executionRepo` must not call `workflowRepo`.
- Repository implementations share clients held by `Data` and may call the
  required database or remote-service client directly.
- `biz` must not depend on sqlc-generated types, SQL rows, table layouts, or
  external SDK types.
- sqlc-generated code and external SDK clients are implementation details of
  data and must not escape through repository interfaces.

## Query Rules

- Prefer direct named SQL queries and straightforward repository code.
- JOINs are opt-in. Use a JOIN only when it has been explicitly approved for
  the concrete query and materially simplifies the implementation.
- Without an approved JOIN, load related rows with batch queries such as
  `ANY($1::type[])` and assemble them in data. Do not introduce N+1 queries.
- Apply filtering, stable ordering, and pagination in SQL before assembling
  results in Go.
- Add indexes for actual filter, JOIN, and ordering paths. PostgreSQL foreign
  keys do not automatically create indexes on referencing columns.
- Keep indexes minimal. Use composite indexes only when the query uses their
  leftmost keys together or needs them to satisfy ordering.
- Use `EXPLAIN` with representative data when index selection matters. An
  index can be available without PostgreSQL choosing it for every data
  distribution.

## Database Layout

Database-related files stay under `db/` so sqlc remains an implementation
detail of the Kratos data layer:

- `db/migrations/` contains versioned schema migration SQL. Use zero-padded
  filenames such as `000001_description.sql`; no migration tool annotations
  are required.
- `db/queries/` contains named queries consumed by sqlc.
- `db/sqlcgen/` is generated by `make sqlc` and must not be edited manually.

The module-level `sqlc.yaml` is the source of truth for these paths.

Do not write unit tests for generated code or imported packages.
